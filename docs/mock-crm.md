# Интеграция CRM и mock CRM

## Назначение и тестовые данные

`mock-crm` — настоящий HTTP-сервис, реализующий предоставленный контракт `POST /client/add-note`. Успешный запрос создаёт **публичную** заметку и возвращает HTTP 201 с JSON `status: success`, `agent`, `client_id` и `message`.

В `mock_crm/fixtures.json` содержатся **исключительно вымышленные**:
- активный агент: `79991234567` (agent ID 123);
- неактивный агент: `79991110000`;
- клиент: `79990000000` (client ID 789);
- второй клиент: `79997654321`;
- два клиента с одинаковым номером `79998887766` для проверки ошибки неоднозначного поиска.

Mock CRM поддерживает ошибки `no_key`, `bad_key`, `empty_note`, `niether_phone_nor_address`, `not_implemented`, `no_user_by_phone`, `no_client_by_phone`, `redundant_client_by_phone` и проверки на некорректные/слишком большие запросы.

Созданные заметки хранятся только в RAM (до 1000), **не сохраняются** в БД, JSON или логах и исчезают после перезапуска контейнера.

## Конфигурация

Скопируйте `.env.example` в локальный `.env` (он уже исключён из Git). Укажите `TELEGRAM_BOT_TOKEN`, подготовьте модель GGUF и переменные Whisper/llama, описанные в основном README.

Для авторизации добавьте:

```dotenv
CRM_API_KEY=<случайный-ключ-не-короче-16-символов>
MOCK_CRM_VIEW_PASSWORD=<другой-случайный-пароль-не-короче-16-символов>
CRM_AGENT_BINDINGS={"123456789":"79991234567"}
CRM_URL=
MOCK_CRM_PORT=8765
```

В `CRM_AGENT_BINDINGS` вместо `123456789` укажите **свой Telegram user ID**. Это явное соответствие Telegram-пользователя номеру сотрудника CRM — `user_phone` нельзя задавать через содержимое заметки. Все неизвестные пользователи и сообщения не из личного чата заблокированы. По умолчанию при пустой привязке нет доступа ни у кого.

Создавайте **два разных** криптографически случайных секрета командой `python -c 'import secrets; print(secrets.token_urlsafe(32))'`. Не помещайте их в Git, документацию, URL или логи.

Пустой `CRM_URL` в Docker Compose означает внутренний адрес mock CRM: `http://mock-crm:8000/client/add-note`. Он доступен боту внутри сети Docker, без публичного проброса API.

## Запуск с mock CRM

```bash
docker compose up -d --build
docker compose ps
docker compose logs -f bot mock-crm
```

**Совместимость с master:** `NoteExtractionService` теперь возвращает шесть полей: лид, тема, описание, следующий шаг, срок и дополнительная информация. Тестовые ФИО и телефон больше не подставляются. Для отправки в CRM лид должен содержать **телефон клиента**, поскольку поиск по адресу в предоставленном API не реализован. Тестовый телефон `79990000000` блокируется при отправке в настоящую HTTPS CRM.

Бот в Compose ожидает сервис `llama`, как и раньше. В интерфейсе бота отправьте/подтвердите заметку, указав в поле «Лид» номер тестового клиента `79990000000` (допускается `+79990000000`). В поле `note` уходят все заполненные **описательные поля**: тема, описание, следующий шаг, срок и дополнительная информация. **Лид не входит в текст заметки**: он используется только как телефон для поиска клиента (`client_phone`). Незаполненные поля не добавляются.

Откройте `http://127.0.0.1:8765/notes` **на машине с Docker**. Браузер попросит HTTP Basic:
- логин: `viewer`;
- пароль: значение `MOCK_CRM_VIEW_PASSWORD`.

Страница показывает номер заметки, понятную дату создания (`ДД.ММ.ГГГГ, ЧЧ:ММ UTC`), ФИО клиента и агента и текст заметки со всеми заполненными описательными полями (без лида). Колонка «Тип» скрыта. `GET /api/notes` возвращает заметки в JSON, включая ФИО и технические ID, и требует те же учётные данные. `GET /health` не содержит клиентских данных.

На сервере порт доступен **только на loopback**. Для удалённого просмотра с локальной машины используйте SSH-туннель:

```bash
ssh -L 8765:127.0.0.1:8765 user@your-server
```

Затем на своём компьютере откройте `http://127.0.0.1:8765/notes`. **Не публикуйте** HTTP Basic UI наружу и не используйте mock CRM с реальными клиентскими данными.

### Миграция старого кэша Whisper

Контейнер бота теперь работает от UID 10001. Если том `whisper_cache` создан предыдущей версией, работавшей от root, его каталог `whisper` может оставаться доступным для записи только root. Это мешает загружать новые модели или заменять повреждённые файлы.

**Один раз перед первым запуском новой версии** остановите старый контейнер бота, мигрируйте права и запустите его снова:

```bash
docker compose stop bot
docker compose --profile maintenance run --rm --no-deps whisper-cache-migrate
docker compose up -d --build bot
```

Сервис `whisper-cache-migrate` **не участвует в обычном запуске**, не получает токены и другие секреты, работает без сети и имеет только одну capability `CHOWN` для изменения владельца. Он использует root строго для этой разовой операции. Сам бот продолжает работать без root и без Linux capabilities. Миграция не удаляет кэш и не меняет файлы моделей.

Ранее приведённая команда `docker compose run --user 0 ... bot chown` не подходит: основной сервис `bot` использует `cap_drop: [ALL]`, а изменение владельца чужих файлов требует capability `CHOWN`.

На новом томе миграция не требуется. Выполняйте команды с тем же Compose project name (тем же `-p` или `COMPOSE_PROJECT_NAME`), что и в прежнем развёртывании. **Не используйте `docker compose down -v`**, иначе существующий кэш будет удалён.

## Запуск только бота (без mock CRM)

Для настоящей CRM укажите её HTTPS endpoint и авторизационный ключ в `.env`:

```dotenv
CRM_URL=https://your-crm.example/client/add-note
CRM_API_KEY=<ключ-реальной-CRM>
CRM_AGENT_BINDINGS={"123456789":"79991234567"}
```

Запустите нужный сервис:

```bash
docker compose up -d --build bot
```

При этом поднимутся бот и его зависимость `llama`, **но mock CRM не запустится**. Если `llama` уже доступна, буквально один контейнер: `docker compose up -d --no-deps bot`. Запуск напрямую `python -m bot.main` использует те же env-переменные.

Произвольный HTTP для внешней CRM запрещён. HTTPS проверяет сертификат, HTTP допускается только для локальной тестовой CRM. Ключ передаётся **в JSON-поле `key`** согласно контракту, не в URL.


### Одна карточка заметки в Telegram

При получении голосового сообщения бот сразу создаёт одну карточку «Голосовое получено. Расшифровываю…» и показывает действие «печатает…». Далее **редактирует это же сообщение** при формировании заметки, выборе поля, вводе исправления и отправке в CRM; ID сообщения сохраняется в FSM-состоянии. Нажатия на устаревшие кнопки не могут повлиять на новую заметку; после успешной отправки или отмены кнопки снимаются. При ошибке CRM текущая карточка возвращается в режим предпросмотра с возможностью исправить поля и повторить отправку после проверки результата в CRM.

Telegram Bot API обычного бота не предоставляет методов для принудительных системных отметок «прочитано» (две галочки) и «прослушано» на входящем голосовом. Вместо них бот показывает своё сообщение о начале обработки. Голосовое и текстовые ответы **пользователя** остаются в истории; только сообщения интерфейса бота объединены в одну карточку. Текущий FSM использует память процесса, поэтому после перезапуска бота предыдущую карточку нельзя автоматически обновить; старые нажатия отклоняются, а их клавиатура удаляется по возможности.

## Обработка ошибок и безопасность

CRM-клиент различает известные коды ошибок API и показывает пользователю фиксированные безопасные сообщения. Если отправка отклонена, черновик остаётся доступным для правки. Сетевой сбой, таймаут, некорректный ответ или ошибка `5xx` дают **неопределённый результат**: автоматического повтора POST нет, поскольку заметка уже могла сохраниться. Сначала проверьте CRM и только потом повторяйте.

Указанный в API-контракте баг (HTTP 500 с корректным JSON `status: success`) учитывается только при проверенном формате успешного ответа. Mock CRM использует ожидаемый HTTP 201.

Bot и mock CRM запускаются без root и лишних Linux capabilities, с read-only filesystem, `no-new-privileges` и ограниченными временными каталогами. Страница заметок требует отдельный пароль, запросы ограничены по размеру, HTML-данные экранируются, браузеру запрещено кэшировать заметки. Бот больше не пишет `transcriptions.log`; удалите старый файл из предыдущих деплоев по правилам хранения данных.

Тесты проверяют контракт HTTP, ошибки авторизации/поиска, просмотр заметок, защиту HTML, связку CRM-клиент ↔ mock CRM, нестандартный успешный HTTP 500 и отсутствие автоматических повторов.

### Изменения после слияния с master

Текущая схема `Note` содержит `lead`, `topic`, `description`, `next_step`, `deadline` и `additional_info`. Действующий API ищет клиента **только по телефону**: адрес в `lead` не может быть отправлен. Если адрес указан вместо телефона, бот не делает запрос в CRM, а предлагает отредактировать лид и оставляет черновик.

Команда `./scripts/ubuntu-deploy.sh` запускает только бота и `llama`, не поднимая mock CRM без необходимых секретов. Чтобы запустить mock, настройте `CRM_API_KEY`, `MOCK_CRM_VIEW_PASSWORD` и `CRM_AGENT_BINDINGS`, затем выполните `docker compose up -d --build`.
