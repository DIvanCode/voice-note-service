# Telegram Voice Notes Bot — Implementation Spec

## 0. Статус документа и приоритет требований

Этот документ описывает техническую реализацию Telegram-бота и должен соответствовать Уставу проекта «Автоматизация создания заметок в CRM из голосовых сообщений Telegram».

Приоритет источников требований:

1. **Устав проекта** — основной и наиболее приоритетный документ.
2. Явно подтвержденные командой технические решения, если они не противоречат Уставу.
3. RACI / распределение ролей — источник границ ответственности компонентов и участников.
4. Этот implementation spec — техническая детализация перечисленных выше требований.

Если новое техническое решение противоречит Уставу, такое противоречие должно быть отдельно и явно подтверждено командой до реализации.

---

## 1. Цель и обязательный продуктовый flow

Сервис позволяет агенту по недвижимости после встречи отправить голосовую заметку в Telegram, получить структурированный результат, проверить/исправить его и после подтверждения передать в CRM.

Целевой flow:

```text
voice
  ↓
Telegram download
  ↓
Speech-to-Text
  ↓
структурирование текста
  ↓
определение темы / ФИО / телефона
  ↓
preview в Telegram
  ↓
валидация и редактирование
  ↓
confirm
  ↓
определение сущности CRM
  ↓
создание заметки в CRM
```

Если тема заметки не определена, заметка **не должна** попадать в CRM. Пользователь получает результат обратно в Telegram и может исправить тему или скопировать заметку вручную.

---

## 2. Проектные требования из Устава

Итоговый MVP проекта должен обеспечивать:

- прием голосовых сообщений от агентов в Telegram;
- преобразование речи в текст;
- структурирование распознанного текста по шаблону;
- определение ФИО клиента;
- определение темы заметки;
- автоматическое определение нужной сущности CRM и привязку заметки к клиенту / контакту / сделке;
- связь Telegram-аккаунта пользователя с аккаунтом CRM для авторизации;
- валидацию и редактирование заметки в Telegram до отправки в CRM;
- отбраковку заметки без темы;
- обработку ошибок на этапах загрузки, распознавания, структурирования и передачи в CRM.

Проектные критерии успешности, которые должны учитываться при дальнейшей интеграции и тестировании:

- точность распознавания речи — 90%;
- не менее 80% заметок длительностью до 5 минут появляются в CRM не позднее чем через 5 минут после окончания записи;
- не менее 95% корректно обработанных заметок автоматически прикрепляются к правильному клиенту / контакту / сделке без ручного выбора или исправления;
- заметки без определенной темы не помещаются в CRM.

Текущий кодовый PR **не доказывает достижение этих метрик**: Whisper уже подключен, но его качество на проектном наборе данных еще не измерено, а реальная LLM/ML-модель и CRM API пока не подключены.

## 3. Scope текущей реализации

### Реализуется сейчас

- Telegram-бот на Python;
- команда `/start` с инструкцией пользователю;
- прием Telegram voice;
- скачивание voice в `bytes`;
- in-memory пользовательский flow;
- реальное локальное распознавание речи через OpenAI Whisper;
- временная тестовая реализация структурирования текста вместо второй ML/LLM-модели;
- модель структурированной заметки;
- preview результата;
- редактирование всех полей заметки;
- запрет отправки заметки в CRM без темы;
- confirm / cancel flow;
- блокировка второго voice, пока текущая заметка не завершена или не отменена;
- явная заглушка CRM;
- обработка ошибок;
- unit-тесты orchestration-логики.

### Намеренно не реализуется сейчас

Пока отсутствуют необходимые контракты / готовые компоненты:

- реальная LLM/ML-функция структурирования;
- реальный CRM API;
- авторизация в CRM;
- привязка Telegram-аккаунта к CRM-аккаунту;
- поиск клиента / контакта / сделки в CRM;
- запись заметки в production CRM;
- измерение проектных метрик на реальных данных.

Для этих частей создаются только четкие границы интеграции. Неизвестное поведение CRM не имитируется и не придумывается.

## 4. Технологический стек

- Python 3.12;
- aiogram 3.x;
- long polling;
- aiogram `MemoryStorage`;
- aiogram `SimpleEventIsolation` для последовательной обработки событий одного FSM-ключа;

- БД;
- repository layer;
- message broker;
- Celery / Kafka / RabbitMQ;
- event bus;
- отдельных HTTP API между ботом и AI-функциями;
- сложного dependency injection;
- distributed tracing;
- кэширования.

## 6. Модель заметки

```python
@dataclass
class Note:
    note: str
    full_name: str | None
    phone: str | None
    topic: str | None
```

Поля:

| Поле | Тип | Назначение |
|---|---|---|
| `note` | `str` | Сформированный текст заметки |
| `full_name` | `str \| None` | ФИО клиента, если удалось определить |
| `phone` | `str \| None` | Телефон клиента, если удалось определить |
| `topic` | `str \| None` | Тема заметки; обязательна для отправки в CRM |

Если ФИО, телефон или тема не определены, соответствующее поле возвращается как `None`.

`topic=None` — отдельный бизнес-сигнал: такую заметку запрещено отправлять в CRM.

## 7. Состояния пользовательского flow

```python
class NoteState(str, Enum):
    PROCESSING = "processing"
    PREVIEW = "preview"
    EDITING = "editing"
    SAVING = "saving"
```

Состояния и содержимое текущей заметки хранятся только в памяти процесса.

Каждая активная заметка получает `flow_id`, связанный с исходным voice message. Все callback-кнопки содержат этот `flow_id`. Callback от старой заметки игнорируется, если его `flow_id` не совпадает с активным flow.

События одного FSM-ключа сериализуются через `SimpleEventIsolation`, чтобы два почти одновременных voice/callback update не могли параллельно пройти проверку состояния и запустить два pipeline или два CRM-вызова.

### Правило одной активной заметки

Пока пользователь находится в любом активном состоянии (`PROCESSING`, `PREVIEW`, `EDITING`, `SAVING`), новое голосовое сообщение не запускает второй pipeline.

Если заметка уже находится в `PREVIEW` или `EDITING`, сообщение о блокировке содержит inline-действия:

```text
[Подтвердить]
[Редактировать]
[Отменить]
```

Если текущее voice ещё находится в `PROCESSING`, кнопки управления не показываются: пользователь получает просьбу дождаться результата. Это исключает гонку, когда текущий pipeline продолжает работу после ручной очистки FSM.

Пользователь должен:

- подтвердить текущую заметку;
- отредактировать ее;
- либо нажать `Отменить`.

После отмены или успешного сохранения FSM очищается.

Перезапуск процесса приложения также очищает in-memory состояние — это допустимое ограничение текущей версии.

## 8. SpeechToTextService

Интерфейс:

```python
class SpeechToTextService:
    async def transcribe(self, audio: bytes) -> str:
        ...
```

Telegram voice приходит в виде OGG/Opus. Whisper принимает путь к аудиофайлу и декодирует его через системный `ffmpeg`.

Текущая реализация:

```text
Telegram OGG/Opus bytes
        ↓
временный *.ogg
        ↓
локальный OpenAI Whisper
        ↓
model.transcribe(path)
        ↓
result["text"]
        ↓
удаление временного файла
```

Модель загружается один раз при создании `SpeechToTextService`:

```python
import whisper

model = whisper.load_model(model_name)
```

По умолчанию используется `large`. Имя модели можно изменить переменной окружения `WHISPER_MODEL`.

Сам вызов `model.transcribe(...)` выполняется в worker thread, чтобы синхронный Whisper не блокировал asyncio event loop Telegram-бота.

`ffmpeg` является системной зависимостью и должен быть доступен в `PATH`.

Временный аудиофайл удаляется в `finally` независимо от успеха или ошибки распознавания.

## 9. NoteExtractionService

Интерфейс:

```python
class NoteExtractionService:
    async def extract(self, text: str) -> Note:
        ...
```

Вход:

```text
распознанный текст
```

Выход:

```python
Note(
    note="...",
    full_name="Иван Иванов",
    phone="+79991234567",
    topic="Покупка квартиры",
)
```

Текущая версия пока не вызывает вторую нейронную сеть. Вместо неё используется временная детерминированная реализация:

```python
Note(
    note=text,
    full_name="Тестовый Клиент",
    phone="+79990000000",
    topic="Тестовая тема",
)
```

То есть распознанный Whisper текст без изменений становится текстом заметки, а остальные поля получают очевидные тестовые значения. Это позволяет проверить весь Telegram user flow до подключения реальной LLM/ML-модели.

Реальная LLM/ML-реализация и prompt остаются следующим этапом.

## 10. TelegramService

`TelegramService` инкапсулирует Telegram-specific операции:

- скачивание voice;
- ответ на `/start` с краткой инструкцией;
- отправку preview;
- inline-кнопки;
- меню редактирования;
- сообщения об ошибках;
- сообщения об успехе / отмене / блокировке второго voice.

Preview:

```text
Тема:
<topic или "не определено">

Заметка:
<note>

ФИО:
<full_name или "не определено">

Телефон:
<phone или "не определено">
```

Если тема определена:

```text
[Подтвердить]
[Редактировать]
[Отменить]
```

Если тема не определена:

```text
[Редактировать]
[Отменить]
```

Кнопка `Подтвердить` не показывается, пока тема отсутствует.

Callback data содержит `flow_id`, поэтому кнопки от старых preview не могут изменить новую активную заметку.

Telegram ограничивает текст сообщения 4096 символами. Для preview длинные значения отображаются сокращённо, при этом полная заметка остаётся без изменений в FSM и используется при редактировании/будущей отправке в CRM.

---

## 11. Редактирование

Пользователь может изменить любое из четырех полей:

```text
[Тема]
[Заметка]
[ФИО]
[Телефон]
```

После выбора поля бот ожидает новое текстовое значение.

Для optional-полей (`topic`, `full_name`, `phone`) символ `-` очищает значение и превращает его в `None`.

Основной `note` не может быть пустым.

После сохранения любого изменения пользователь снова получает Preview.

Если тема была добавлена вручную, становится доступна кнопка `Подтвердить`.

## 12. CRMService

Интерфейс текущей версии:

```python
class CRMService:
    async def create_note(self, note: Note) -> None:
        ...
```

Текущая реализация — **явная заглушка**.

При попытке подтвердить заметку с заполненной темой текущая CRM-заглушка сообщает, что CRM пока не подключена, после чего текущая заметка автоматически отменяется и FSM очищается. Пользователь может сразу отправить новое голосовое сообщение.

После получения реального CRM-контракта `CRMService` должен инкапсулировать минимум:

```text
Telegram account
        ↓
CRM authorization / account binding
        ↓
поиск правильного клиента / контакта / сделки
        ↓
создание заметки
        ↓
подтверждение успешного сохранения
```

Handlers не должны знать URL, схему авторизации или детали CRM API.

## 13. Handlers

### VoiceHandler

Отвечает только за orchestration:

```text
check no active flow
    ↓
PROCESSING
    ↓
download voice
    ↓
STT
    ↓
extraction
    ↓
save Note to memory
    ↓
PREVIEW
```

При ошибке состояние очищается, чтобы пользователь мог повторить попытку.

### NoteEditHandler

Отвечает за:

- вход в режим редактирования;
- выбор поля;
- обновление поля;
- возврат к Preview;
- отмену текущей заметки.

### NoteConfirmationHandler

Перед CRM обязан повторно проверить наличие темы, даже если callback был получен некорректно или устарел.

```text
Confirm
   ↓
validate topic
   ↓
SAVING
   ↓
CRMService.create_note()
```

До подключения CRM заглушка возвращает контролируемую ошибку. После этой ошибки текущая заметка автоматически отменяется, FSM очищается, и пользователь может сразу отправить новое voice.

После будущего успешного сохранения состояние очищается и пользователю показывается success message.

---

## 14. Ошибки и защита пользовательских данных

Клиентские данные допускается хранить только временно в процессе обработки.

Запрещено сохранять в БД, файлах приложения или пользовательских логах:

- voice/audio;
- transcript;
- текст заметки;
- ФИО;
- телефон;
- другие клиентские данные.

Допускается техническое логирование без пользовательского содержимого, например:

```text
Voice processing failed (SpeechToTextNotConfiguredError)
CRM save failed (TimeoutError)
```

Нельзя логировать текст exception, если он потенциально содержит пользовательские данные.

Временный аудиофайл для Whisper удаляется после обработки.

## 15. Тестирование текущей версии

Unit-тестами должны быть покрыты минимум:

1. `voice -> Whisper -> extraction stub -> preview` orchestration;
2. блокировка второго voice;
3. очистка FSM при ошибке обработки;
4. вызов Whisper-модели и нормализация результата;
5. удаление временного `.ogg` после STT-вызова;
6. работа временной реализации второй модели;
7. ответ на `/start`;
8. редактирование поля;
9. ручное добавление темы;
10. очистка optional-поля;
11. запрет CRM-вызова без темы;
12. успешный confirm при подмененном fake CRM;
13. автоматическая очистка FSM после подтверждения при CRM-заглушке;
14. наличие действий `Подтвердить / Редактировать / Отменить` в сообщении о блокировке второго voice;
15. отсутствие этих действий во время `PROCESSING`;
16. сериализация событий одного пользователя через FSM event isolation;
17. игнорирование callback-кнопок от устаревшего `flow_id`;
18. безопасное сокращение preview длиннее Telegram message limit без изменения полной заметки в FSM.

Реальные метрики распознавания, структурирования, скорости и CRM-привязки проверяются только после подключения соответствующих компонентов.

## 16. Definition of Done текущего PR

Текущая техническая итерация считается готовой, если:

- бот запускается на Python 3.12 + aiogram 3.x;
- команда `/start` показывает пользователю инструкцию;
- Telegram voice скачивается в `bytes`;
- второй voice не запускает параллельную заметку;
- локальный Whisper реально выполняет STT;
- Whisper безопасно работает с временным OGG-файлом и не блокирует event loop;
- вторая модель временно заменена детерминированной тестовой реализацией;
- `Note` содержит `note`, `full_name`, `phone`, `topic`;
- заметка хранится только в памяти;
- Preview показывает все поля;
- все четыре поля можно редактировать;
- заметка без темы не может быть отправлена в CRM;
- текущую заметку можно отменить;
- CRM представлена честной заглушкой без придуманного API;
- подтверждение при CRM-заглушке автоматически завершает текущий flow и очищает заметку;
- при попытке отправить второй voice в `PREVIEW/EDITING` пользователь получает кнопки `Подтвердить / Редактировать / Отменить`;
- события одного FSM-ключа выполняются последовательно;
- callback-кнопки привязаны к конкретному `flow_id` и не могут управлять новой заметкой из старого preview;
- длинный preview не превышает Telegram message limit, а полное значение заметки сохраняется в памяти;
- ошибки не приводят к постоянному сохранению пользовательских данных;
- unit-тесты orchestration проходят.

Это **не** означает готовность полного проектного MVP: production CRM-интеграция, авторизация, автоматическая привязка и реальные AI-компоненты остаются обязательными дальнейшими работами согласно Уставу.
